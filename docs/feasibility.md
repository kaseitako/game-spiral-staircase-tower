螺旋階段の塔：実現可能性と技術選定メモ
========================================

検討日：2026-10-22。このメモは実装前の技術選定を記録したもの。以下の技術情報・未決定事項・寸法案は検討当時の内容であり、現行仕様ではない。現在は Three.js を採用し、入口は1周ごと、専用操作による落下・帰宅とタッチ用移動ボタンを実装している。プロトタイプの実装内容・起動方法・検証結果は [README](../README.md) を参照。

十分に実現可能。コード中心で作る場合は **TypeScript + Vite + Three.js** を第一候補とする。塔と階段を規則的に生成でき、個人用の小さな散策ゲームとして構成しやすい。制作の重点は、自動カメラ、階段の歩き心地、白い霧の中での見え方に置く。

音は任意。最初の試作は無音とし、必要になれば環境音のループを追加する。

**要件と仮定**

| 区分 | 内容 |
|---|---|
| ユーザーの要件 | ブラウザ、ローポリ、三人称、操作不要の追従カメラ |
| ユーザーの要件 | 細い円柱状の塔、柵のない狭い外周の螺旋階段、上下への際限のない移動 |
| ユーザーの要件 | 約5階分の高さごとの入口と、休める小さな室内 |
| ユーザーの要件 | 上下の端も周囲の地形も見えず、遠方は白い靄に溶ける |
| ユーザーの補足 | 個人で遊ぶ用途。音はなくてもよく、簡単なら追加 |
| 検討上の仮定 | 最初は本人が使うPCのブラウザ、1人用、キーボード操作 |
| 未決定 | 落下の有無、階段上で横移動できる範囲、スマートフォン対応 |

**技術の選択肢**

以下の適性評価は、このゲームの規模と構造に対する設計判断。

| 候補 | 今回の利点 | 自分で作る部分・制約 | 選ぶ条件 |
|---|---|---|---|
| Three.js + TypeScript + Vite | 塔・階段・霧をコードで直接調整しやすい。必要な処理を絞れる | 移動、カメラ、衝突、保存を組み立てる | コード中心で小さく作る場合の第一候補 |
| Babylon.js + TypeScript + Vite | カメラ、衝突、アニメーション等の機能が揃う | 螺旋用の追従や室内への遷移は個別調整が必要 | 自由歩行や物理的な挙動を早く扱いたい場合 |
| Godot + GDScript | エディタで部屋や家具を配置する作り方に向く | Web出力の描画方式・言語の制約を踏まえて制作する | 視覚的に配置・調整する作業を重視する場合 |

Three.js の WebGLRenderer は WebGL 2 を使用する。今回の表現はこの描画方式を前提に設計でき、WebGPUを必須にする理由はない。[Three.js公式](https://threejs.org/docs/pages/WebGLRenderer.html)

Babylon.js には追従カメラ、衝突処理、霧、インスタンス描画などが用意されている。ただし既製の追従カメラだけで、この塔の見やすさが保証されるわけではない。[Babylon.js公式](https://www.babylonjs.com/specifications/)

Godot 4 のWeb出力は、現在の公式資料では Compatibility レンダラーと WebGL 2 が前提で、C#のプロジェクトはWeb出力できない。選ぶなら GDScript とシングルスレッド出力から始める。Webの標準Sample音声には残響などの制約があるが、無音または単純な環境音でよい今回の選定では優先度が低い。[Godot公式](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

Vite は開発サーバーと静的ファイルへのビルドを提供する。今回の1人用構成では、ゲーム状態を管理する専用サーバーやデータベースを設ける必要はない。[Vite公式](https://vite.dev/guide/)

Blender はモデルとアニメーションを glTF / GLB で出力できる。家具や人物の品質を上げたくなったときに導入する。[Blender公式](https://docs.blender.org/manual/en/5.3/addons/scene_gltf2.html)

React等のUIフレームワークも初期段階では必要性が低い。画面に置くのが開始・停止・設定程度なら、通常のHTMLで足りる。

**無限の塔を作る方法**

1. 塔を一定の高さごとの区間に分け、プレイヤーの周囲だけ生成する。
2. 霧に完全に隠れる距離よりも余裕を持って上下の区間を用意し、遠くの区間を再利用・解放する。
3. 区間番号と固定の種から部屋を選ぶ。下って戻ったときにも同じ場所に同じ部屋が現れるようにする。
4. 位置は「区間番号＋区間内の位置」で管理し、描画する座標はプレイヤー付近へ定期的に移す。長距離移動で座標が巨大になり、表示や衝突が揺れることを避ける。
5. 開始地点から上にも下にも区間を生成し、塔の底や頂上は設けない。

同じ形の階段は区間ごとにまとめてインスタンス描画する。Three.js の InstancedMesh は、同じ形状・材質の物体をまとめて描く用途に使える。[Three.js公式](https://threejs.org/docs/pages/InstancedMesh.html)

霧は遠くを見えにくくする表現であり、それだけでは物体数や衝突処理は減らない。区間の生成数・描画対象・衝突対象を実際に制限する。部屋の内容も、訪問履歴を無制限に保存せず、まずは区間番号から再現する。

塔は中へ入れるように壁を分割して作り、入口のある区間には開口部を用意する。部屋を置く場所まで中身の詰まった円柱にする必要はない。入口の前には、階段から室内へ安全に移れる小さな水平の足場を置く。

**寸法の初期案**

以下は建築仕様ではなく、見た目と操作を検証するための仮の寸法。

| 項目 | 仮の値 | 理由・補足 |
|---|---|---|
| 塔の外径 | 約5m | 6畳程度の四角い部屋を収めるなら、床面積だけで直径を決めない |
| 室内の内径 | 約4.6m | 仮に2.7m × 3.6mの部屋なら対角線は4.5m。壁厚も別に必要 |
| 階段幅 | 約0.8m | すれ違えない細さを表現し、キャラクターの幅と合わせて調整 |
| 一段の高さ | 約0.17m | 歩行アニメーションと段差表現を合わせる初期値 |
| 一周の段数 | 約45段 | 階段中央の半径2.9mなら、一段の奥行きは約0.40m |
| 一周の上昇量 | 約7.65m | 45段 × 0.17m |
| 部屋の間隔 | 約2周、約15mの高さ | 1階分を約3mと仮定した「5階分」に相当 |

踊り場を除く上記の概算では、部屋の間の歩行距離は約40m。毎秒0.65mで歩けば約1分となる。実際の休憩間隔は、階数の再現だけで決めず、歩いて落ち着ける長さで調整する。

**先に解決する難所**

| 難所 | 起こりやすいこと | 対応案 |
|---|---|---|
| 螺旋に沿う自動カメラ | 塔の壁に遮られる、回転が忙しい | キャラクターの斜め後ろ・外側に置き、塔を回る角度に沿って滑らかに追従 |
| 上りから下りへの切り替え | カメラが急に180度回る、入力方向が混乱する | 進行方向と入力の関係を固定し、方向転換の時間を調整 |
| 階段の歩行 | 段差で身体と画面が小刻みに跳ねる | 見た目は段、移動の高さは滑らかな経路で計算。足の接地は必要に応じて補正 |
| 狭い室内 | 後方にカメラを置く空間が足りない | 距離を短くし、必要なら室内用の固定アングルへ穏やかに切り替える |
| 長く遊ぶと負荷が増える | 過去の区間・モデル・音源が残る | 保持する区間数を固定し、再利用・解放を確認 |

最初は、階段の上り下りを経路に沿って操作し、入口付近で室内へ移れる方式を推奨する。これは柵のない見た目を保ちながら、転落を気にせず歩くための設計案であり、ユーザーが指定した操作仕様ではない。

自由に横へ歩いて落下できるようにする場合は、身体の衝突形状、段差、復帰地点を追加で設計する。Rapier は段差・斜面を扱うキャラクターコントローラーを備えるが、この階段に合う調整は必要。[Rapier公式](https://rapier.rs/docs/user_guides/javascript/character_controller/)

**無音でもアンビエントな雰囲気を作る方針**

- 白に少し灰色を混ぜた背景と距離霧を合わせ、塔の上下が自然に消えるようにする。遠方が距離に応じて霞む基本表現には Three.js の Fog が使える。[Three.js公式](https://threejs.org/docs/pages/Fog.html)
- 足元数段ははっきり見せ、遠くほど輪郭と色の差を小さくする。
- 外は明るく拡散した光、室内は少し暗い光にして、入った瞬間の落ち着きを作る。
- ローポリの大きな面と控えめな色数を使い、階段の厚みや壁の陰影を残す。
- 歩く速度と方向転換をゆっくりにし、カメラの上下動は抑える。
- 部屋は手作りの少数の型にする。空室、傷んだ壁と椅子、布や寝床のある部屋などを組み合わせ、家具の配置だけ少し変える。
- 休む行為は立ち止まる・座る・外を眺める程度から始める。疲労ゲージや回復アイテムは初期案に含めない。

音を追加する場合は、開始ボタンの操作後に小さな環境音をループし、ミュートできれば足りる。ブラウザは音声の自動再生を制限する場合があるため、開始操作に再生を結び付ける。[MDN](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)

**試作する順序と評価点**

| 段階 | 作るもの | 確かめること |
|---|---|---|
| 1. 空間の試作 | 塔、階段数周、仮の人物、追従カメラ、白い霧、無音 | 上下に歩くだけで雰囲気があるか。階段が読めるか。カメラが忙しくないか |
| 2. 部屋の試作 | 入れる部屋1つ、入口、簡単な家具 | 外から中への移動と画角が自然か。部屋で立ち止まりたくなるか |
| 3. 継続して遊べる形 | 上下の区間生成、同じ部屋の再現、位置保存 | 長時間の上下移動で継ぎ目が見えないか。負荷が増え続けないか |
| 4. 雰囲気の調整 | 歩行、材質、数種類の部屋、任意の環境音 | 要素を増やすことで落ち着いた体験が良くなるか |

対象PCで滑らかに動くことを確認し、目安として60fpsを狙う。これは性能保証ではなく試作の目標値。スマートフォンも対象にするなら、操作方法・解像度・影の設定をその端末で別途確認する。

次に実装へ進む場合は、第1段階の小さな空間で歩行とカメラを確かめる。技術スタックの確定と無限生成への着手は、その手触りを見て判断できる。
